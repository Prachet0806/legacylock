# LegacyLock deployment contract

Production activation requires the checks below and current dependency audits. Local tests do not establish real email delivery, HTTPS cookie behavior, offsite backup objectives, capacity or independent cryptographic review.

## Current deployment: Render Free + Neon Free

**Services:** Vercel frontend → same-origin `/api/*` rewrite → one Render Free web service from `backend/Dockerfile` → Neon Free PostgreSQL. This is the currently selected deployment footprint. It uses one Uvicorn process with the in-process scheduler; there is no separate worker or Render one-off migration job. Render documents that Free web services spin down after 15 minutes without inbound traffic, may restart, and should not be used for production applications ([Free plan limits](https://render.com/docs/free)). Neon Free compute can autosuspend after inactivity and the current Free plan includes a limited instant-restore window; verify current account limits in Neon’s [Free plan documentation](https://neon.com/pricing). These limits mean the chosen footprint is not production-qualified and does not establish a recovery objective. The alternate paid, separate-worker path appears below.

Set the Render API environment from [`deploy/api.demo.env.example`](deploy/api.demo.env.example). The execution settings are `ENVIRONMENT=production`, `TASK_MODE=single_process_demo`, `BACKGROUND_IN_API=false`, `DEMO_CHECK_INTERVAL_SECONDS=1800`, `DEMO_DELIVERY_BATCH_SIZE=5`, `DEMO_ARGON2_CONCURRENCY=1`, `DB_POOL_SIZE=3`, and `DB_MAX_OVERFLOW=0`. Set the remaining database, TLS, key, sender, release-control, origin, and monitor secrets in Render's secret store. `DB_POOL_SIZE` must be at least 2 because the advisory lock holds one connection during a pass. The Docker command explicitly starts one Uvicorn worker. Do not run `worker.py` in this mode.

The lifespan scheduler checks overdue heartbeats and sweeps the durable outbox at startup. It then evaluates heartbeats every 30 minutes, wakes after committed jobs, schedules retries and expired leases by their due times, and runs periodic recovery sweeps. PostgreSQL advisory locks prevent overlapping passes during replacement; they do not elect a single scheduler leader for its entire lifetime. Keep the Render service at one instance.

**Migration before first deploy:** Create the intended Neon Free project and copy its *direct* connection URL. From a trusted local machine or CI job with reviewed backend dependencies and private Neon credentials, set `DATABASE_URL` with `sslmode=verify-full`, a readable local `PGSSLROOTCERT` (the container path in the example is not a Windows path), and the other required API secrets. Run `python preflight.py api`, `alembic upgrade head`, and `alembic current` from `backend/`; verify revision `0009_verified_recovery`. Run the migration before starting the Render service and repeat it as a reviewed maintenance step when schema updates are needed. There is no managed Render one-off migration job in the Free plan. Production API startup never creates or migrates tables. Do not place Neon credentials or signing keys in Vercel, the repository, or CI logs.

Build the frontend natively from `frontend/` with `npm ci` and `npm run build`. Set `NEXT_PUBLIC_API_URL=/api` and `API_UPSTREAM=<Render HTTPS API origin>` on Vercel. Use an isolated preview API and Neon project; the preview build requires distinct `PREVIEW_API_UPSTREAM` and `PRODUCTION_API_UPSTREAM` values. Keep the `RELEASE_HOLD` and `DELIVERY_ENABLED` controls at their initial guarded values until the controlled fixture and sender are qualified.

Monitor Render `/health` with UptimeRobot every five minutes. It is database-free and proves HTTP liveness only. Check `/scheduler-health` for scheduler freshness, `/readyz` for database access, and authenticated `/operations/recovery` for checkpoints, pending jobs, overdue work, and provider outcomes. The owner dashboard refreshes scheduler status every minute and on window focus. Database-backed monitoring can wake Neon; avoid a five-minute database poll when testing autosuspend. Configure an actual alert recipient. A keep-warm monitor cannot prevent restarts or platform outages.

Before treating this deployment as qualified, exercise a Render restart, Neon autosuspend/reconnect, a committed verification and invitation email, retry and expired-lease recovery, and heartbeat evaluation while API requests run. Measure memory and CPU in the actual Render Free environment. The local [free-tier baseline](docs/free-tier-worker-baseline.md) uses local Windows/Docker fixtures and does not prove hosted capacity or Neon behavior.

## Optional paid API and independent worker deployment

This is an alternate topology, not the currently selected Free deployment. Use it only after deliberately moving off the Render Free + Neon Free footprint and qualifying the paid services, migration process, backups, and operational controls.

### Topology and artifact

Browser → Vercel HTTPS application origin → same-origin `/api/*` rewrite → Render FastAPI service → Neon PostgreSQL. A second, private Render service runs `python worker.py` continuously for checker passes and delivery attempts. Keep one API instance while rate limits use process-local buckets. Rolling replacement also needs edge enforcement if the limit must span old/new instances. Never trust arbitrary forwarded headers to improve client-IP attribution.

Build the backend image from the reviewed tree and use a native Vercel build from `frontend/` with `npm ci` and `npm run build`. Targets are Python 3.12.14 and Node 22.23.3; install locked dependencies. Set `NEXT_PUBLIC_API_URL=/api` and `API_UPSTREAM=<Render production HTTPS API origin>` for production. For Vercel previews set `PREVIEW_API_UPSTREAM=<isolated HTTPS fixture API origin>` and `PRODUCTION_API_UPSTREAM=<production HTTPS API origin>`; the build rejects a missing or shared preview origin. The Next.js rewrite is the sole `/api` route. The frontend Docker image is a diagnostic artifact whose standalone `server.js` needs `.next/static` colocated.

`render.yaml` is a historical deployment example and is not used for this topology. Configure exactly one paid Render API service from `backend/Dockerfile`, one independent paid worker service from the same reviewed image, and a paid one-off migration job before deploying the worker. The image has no default HTTP health check because the worker has no HTTP listener: configure `/health` and `/readyz` probes for the API, and monitor worker process state plus authenticated `/operations/recovery` checkpoint freshness separately. Gate automatic promotion of API and worker so schema and sender cutover stay coordinated. Qualify the actual accounts, quotas and host behavior before storing real user data. Verify the selected Neon's restore window and test encrypted offsite backups separately; [Neon's backup guide](https://neon.com/docs/manage/backup-pg-dump) distinguishes in-platform history from off-platform copies.

The intended use recorded for this project is real user data and non-commercial. The currently selected Render Free + Neon Free footprint is a deployment target, not production approval: Render's published Free plan guidance says not to use it for production. Do not claim production readiness until the hosting choice, backups, restore evidence, and release gates are reviewed. Confirm the actual Vercel account terms and capacity. See the [current deployment roadmap](docs/deployment-roadmap-2026-11-03.md).

### Configuration for the optional paid topology

| Setting | Contract |
|---|---|
| `ENVIRONMENT` | `production` on API and worker |
| `DATABASE_URL` | Direct Neon PostgreSQL connection string for the initial fixed-size API and worker, with `sslmode=verify-full`; retain `channel_binding=require` if Neon supplies it. Use a separate Neon project for previews and synthetic tests |
| `PGSSLROOTCERT` | Readable system CA bundle path (`/etc/ssl/certs/ca-certificates.crt` in the backend image), or set `sslrootcert` in `DATABASE_URL` |
| `SESSION_SECRET` | Dedicated random value, at least 32 characters |
| `AUTH_EPOCH` | Deployment-wide identifier, synchronized on API/worker; replace after restoration |
| JWT signing keys | Corresponding RSA private/public PEM pair, at least 2048 bits. API validates correspondence at startup. Supply readable files via `JWT_PRIVATE_KEY_PATH`/`JWT_PUBLIC_KEY_PATH`, or base64-encoded PEMs via secret-store `JWT_PRIVATE_KEY_B64`/`JWT_PUBLIC_KEY_B64` when mounted file permissions prevent non-root access. Worker needs neither key |
| `DELIVERY_PAYLOAD_KEY` | Separate random 32-byte base64 AES-GCM key, backed up outside the database |
| `DELIVERY_PAYLOAD_KEY_ID`, `DELIVERY_PAYLOAD_KEYS` | Current version and secret JSON ring of retained older versions; do not retire a version with live/retained payloads |
| `ALLOWED_ORIGINS`, `FRONTEND_URL` | Exact application HTTPS origin; no wildcard or `null` |
| `ALLOWED_HOSTS` | Actual API hostnames, including platform health/rewrite host |
| `TRUSTED_PROXIES` | Verified direct-peer and forwarding-chain CIDRs only. Start Uvicorn with `--no-proxy-headers`; the application owns trust parsing |
| `BACKGROUND_IN_API` | `false` with the separate worker |
| `DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, `DB_POOL_TIMEOUT` | Bounded SQLAlchemy connections against the selected Neon compute's direct connection limit; defaults 3, 0, 10 seconds per process; verify total API plus worker connection usage |
| `MAX_BENEFICIARIES_PER_VAULT`, `MAX_MESSAGES_PER_VAULT` | Admission limits, defaults 25 and 100; tune only after hosted capacity measurement |
| `HEARTBEAT_ENABLED` | `true` for recovery checking |
| `RELEASE_HOLD` | Initially `true` on both processes; release only after reconciliation and evidence review |
| `DELIVERY_ENABLED` | `false` during restore quarantine; enable deliberate delivery after reconciliation |
| `RESEND_API_KEY`, `NOTIFICATION_EMAIL_FROM` | Real verified sender/account; missing email credentials fail production startup. Verify domain, quota and delivery using a controlled recipient |
| `OPERATIONS_TOKEN` | Separate random credential of at least 32 characters for the API's restricted recovery-health monitor |
| `REGISTRATION_INVITE_CODE` | Out-of-band operator enrollment code; empty disables registration |
| `SMS_ENABLED` | `false` unless SMS credentials, recipient preferences and delivery are separately qualified |

Host-only HttpOnly cookies are `Secure` in production, `SameSite=Lax` and scoped to the application path through `/api`. Qualify login, refresh, logout and both role cookies on the actual HTTPS hostname. A localhost test cannot verify Secure cookie transport through a hosted proxy.

Use `deploy/api.production.env.example` and `deploy/worker.production.env.example` as inventories for the two Render secret stores. The worker shares the database, epoch, delivery key ring, sender, and release controls with the API; it does not receive JWT signing keys or the operations monitor token. Use `deploy/frontend.production.env.example` for Vercel Production and `deploy/frontend.preview.env.example` for Preview. Set each variable in the target service or Vercel environment before building; do not upload a populated template. The local root `.env` and `docker-compose.yml` are development-only.

Copy the direct connection string from Neon's Connect dialog. Its default `sslmode=require` must be changed to `sslmode=verify-full`; preserve the hostname, credentials, database, and `channel_binding=require` option. Set `PGSSLROOTCERT=/etc/ssl/certs/ca-certificates.crt` in the API, worker, and migration job; the backend image installs that CA bundle. [Neon's secure connection guide](https://neon.com/docs/connect/connect-securely) describes full certificate and hostname verification. Use the same Neon branch/database for API and worker. The one-off migration and offsite `pg_dump` jobs use the **direct** Neon connection; Neon's [pooling guide](https://neon.com/docs/connect/connection-pooling) notes that schema migrations and dumps should use direct connections. Start the bounded API and worker pools on direct connections as well; qualify locking, connection limits, and retries before considering a pooled runtime endpoint.

The worker polls and records database checkpoints throughout the day, so budget the production Neon compute as an active service and measure first-request latency after idle periods in the hosted fixture. Do not assume scale-to-zero savings for this topology; this is an inference from `backend/worker.py` and [Neon's scale-to-zero behavior](https://neon.com/blog/using-neons-auto-suspend-with-long-running-applications).

With each service's real environment in place, run `python preflight.py api` in the API image and `python preflight.py worker` in the worker image. Both commands check static configuration without contacting PostgreSQL or the email provider. API startup also refuses a missing or short `OPERATIONS_TOKEN`. Vercel's environment values apply to a new deployment, not one already built; redeploy after changing the upstream. [Vercel environment documentation](https://vercel.com/docs/environment-variables) describes this scope.

`scripts/deploy-qualify.sh --api <HTTPS API> --app <HTTPS app> --expect-hsts` performs anonymous routing/origin/health checks. For a controlled owner fixture, supply `--owner-email` and inject `QUALIFY_OWNER_PASSWORD` privately; the authenticated phase uses the app's `/api` path for login, refresh and logout. It does not trigger or wipe a vault. This script is only one qualification component and has not been run against a hosted deployment here.

### New empty Neon database and sole sender

1. In the [Neon Console](https://console.neon.tech/), create an empty production project in a region near the API host. Create a separate preview/test project with synthetic data. Record each project, branch, database, region, Postgres version, selected plan limits, and direct connection host without recording credentials in the release log.
2. In the production project, click **Connect**, choose the production branch, compute, database, and role, then turn **Connection pooling off** and copy the direct string. [Neon's connection guide](https://neon.com/docs/connect/connection-pooling) documents this toggle. Change only `sslmode=require` to `sslmode=verify-full`, retaining `channel_binding=require` if supplied. Store that URL privately as `DATABASE_URL` for the API, worker, and one-off migration job; do not put it in Vercel or `NEXT_PUBLIC_*` variables. Set `ENVIRONMENT=production`, `PGSSLROOTCERT`, a shared fresh `AUTH_EPOCH`, `RELEASE_HOLD=true`, and `DELIVERY_ENABLED=false`. Keep only one active worker/sender. Run the API and worker preflight checks; verify the intended Neon host and branch in the secret-store settings without printing the URL.
3. Run `alembic upgrade head` exactly once from a one-off job using the reviewed backend image and direct Neon connection. Confirm `alembic current` reports `0009_verified_recovery`; production app startup never creates or migrates tables. Start the API and worker only after this succeeds.
4. Verify `/health`, `/readyz`, the worker's checker and delivery checkpoints, and the recorded hold (`python ops.py --record-hold`). Exercise row locking, outbox claims, TLS verification, connection limits, and a Neon compute restart in the isolated hosted fixture.
5. Configure a scheduled encrypted offsite backup from the **direct** Neon endpoint, separate key escrow, failure alerts, and a timed restore into a different isolated project. Do not count Neon restore history alone as an offsite backup.
6. Enable delivery deliberately for controlled registration, invitation, and beneficiary sign-in tests while release hold remains active. Verify provider acceptance and inbox receipt. Lift release hold only after the full release/recovery journey and evidence review; record the resulting configuration again.

This path assumes the Neon database is empty. If vault data is later imported from another provider, plan a separate inventory, dump/restore, reconciliation, key/epoch, and sender cutover; do not treat a credential change as a data migration. [Neon's migration tools](https://neon.com/migration) describe import and dump/restore options. On regression, restore the hold, stop sending, retain the expanded schema, and use a compatible reviewed application or forward repair. Never restore a database under an old authentication epoch.

### Monitoring and release gates

`/health` proves process liveness; `/readyz` proves database connectivity. Restricted `/operations/recovery` distinguishes stale/error checkpoints, release holds, overdue jobs, expired leases, dead letters, pending-release lag and recent provider attempt outcomes. Recovery degradation must alert without taking owner check-in routes offline. Configure monitor authorization privately and verify an actual alert recipient; configuration documents are not evidence that alerts are wired.

The CI workflow runs SQLite/PostgreSQL suites, production browser journeys, dependency/quality gates and image asset checks. Qualify the Render services, secret access, Vercel HTTPS `/api` routing, Neon connection and transaction behavior, real providers, recovery alerts, offsite restore and an independent cryptographic review before production activation. Load-test the expected inventory to establish capacity and measured processing budget. Proposed RPO 15 minutes/RTO four hours remain targets until a timed offsite restore demonstrates them.
